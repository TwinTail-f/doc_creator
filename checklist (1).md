# Спека агента: ревью и исправление тестов (autodoc)

## 0. Контекст

Тебе передают тестовые файлы/папки (`tests/...`, pytest), часть которых
писала LLM и частично поправил человек. Задача — не переписывать тесты
с нуля, а пройтись по чек-листу (раздел 2) по каждому переданному файлу,
найти совпадения с антипаттернами и исправить именно их, минимально
трогая остальное.

Стек: `pytest`, `pydantic` v2, `tmp_path`, маркеры `@pytest.mark.business_logic`
/ `contract` / `infrastructure` / `integration` (определения — в категории L).

## 1. Как работать

1. **Скоуп** — только переданные файлы. `autodoc/*` не трогать; найденный
   в нём реальный баг — отдельным пунктом в отчёте, не чинить заодно.
2. Проверяй каждый файл на **все** категории A–M; одна проблема может
   попадать под несколько сразу — правь под все применимые.
3. **Не теряй покрытие** при слиянии тестов: новый параметризованный тест
   обязан покрывать все кейсы старых один к одному. Молчаливое удаление
   кейса запрещено — либо перенести, либо обосновать в отчёте.
4. При слиянии тестов с разными маркерами — выбери маркер по смыслу
   объединённого теста; если неоднозначно — TODO-комментарий + вопрос в отчёт.
5. **Минимальный дифф** — не переименовывай/не форматируй то, что не
   относится к найденной проблеме; не трогай тесты вне чек-листа.
6. После правок мысленно прогони `pytest` по файлу — фикстуры/параметры/
   импорты не должны разъехаться.
7. **Отчёт** — короткий список по каждому изменённому файлу: что и по
   какой категории (A–M) поправлено. Неприменимые пункты не упоминать.

## 2. Чек-лист антипаттернов

### A. Тест проверяет чужую библиотеку, а не код проекта
**Симптом.** Тест доказывает поведение `pydantic`/`urllib3`/арифметики
Python, а не логику `autodoc`. Тест: «если бы автор `autodoc` сломал
свою функцию — упал бы этот тест?» Если нет — категория A.
Пример: `backoff_factor * (2**0) < backoff_factor * (2**1)` — это `2**1 > 2**0`,
не поведение `RetryableSession`.

**Как чинить.**
- Нет собственной обработки в проекте (голое исключение сторонней
  библиотеки) → тест удалить.
- Есть обработка (`ConfigManager` ловит `ValidationError` → `ConfigError`)
  → тестировать переход через публичный API проекта, не сырое исключение.
- Числа/тайминги → проверять наблюдаемое поведение объекта проекта
  (например, реальную задержку при замоканном `time.sleep`), а не
  формулу, скопированную в сам тест.

---

### B. Тест «положил — достал»
**Симптом.** В конструктор передаётся значение поля, ассерт проверяет
то же значение без единой трансформации/валидации/ветвления между ними —
это механика pydantic, не бизнес-правило.
Пример: `ConanInputOptions(parsed_options=explicit)` → `assert instance.parsed_options == explicit`.

**Как отличить.** Если объект реально что-то решает (например,
автозаполняет поле, но не перезаписывает явно заданное) — не категория B,
но обе ветки этого правила приоритета объединяются в один параметризованный
тест (см. категорию C), а не остаются раздельными тестами.

**Как чинить.** Тавтологичный тест — удалить. Если это ветка правила
приоритета — слить обе ветки в один `@pytest.mark.parametrize` с `id=`
на каждый кейс.

---

### C. Дублирующиеся тесты вместо параметризации
**Симптом.** Несколько тестов с почти идентичным телом, отличающихся
только литералами (расширение файла, формат, входная строка), либо
«слабый»/«строгий» вариант одной проверки в разных тестах
(`is not None` vs `isinstance(...)` при идентичном сетапе).

**Как чинить.**
- Слить в `@pytest.mark.parametrize` с `pytest.param(..., id="...")`.
- Комментарий-намерение каждого кейса — над соответствующим `pytest.param`,
  не теряется при слиянии.
- Из пары «слабый/строгий» тест — оставить только строгий вариант,
  слабый удалить целиком (не переносить как отдельный кейс).

```python
@pytest.mark.parametrize(
    "filename, dump",
    [
        pytest.param("parser_config.json", json.dumps, id="json"),
        pytest.param("parser_config.yaml", yaml.dump, id="yaml"),
        pytest.param("parser_config.yml", yaml.dump, id="yml-extension"),
    ],
)
def test_config_manager_loads_valid_config_by_extension(
    tmp_path: Path, filename: str, dump: Callable[[dict], str],
) -> None:
    config_file = tmp_path / filename
    config_file.write_text(dump(_VALID_PARSER_CONFIG), encoding="utf-8")
    manager = ConfigManager(configs_dir=tmp_path)
    assert isinstance(manager.load_parser_config(filename), ParserConfigSchema)
```

### D. Тест проверяет детали реализации, а не наблюдаемое поведение
**Симптом.** Ассерты лезут во внутренние атрибуты чужого объекта
(`retry.status_forcelist`, `retry.total`) вместо вызова публичного метода
и проверки результата.

**Как чинить.** Используй `responses` (или аналог мока HTTP на уровне
`requests`): зарегистрируй последовательность ответов (`429`, `429`, `200`)
и проверь наблюдаемый результат — число реальных запросов и итоговый ответ,
а не факт наличия кода в конфиге ретраев.

```python
@responses.activate
def test_retryable_session_retries_until_success_on_429() -> None:
    responses.add(responses.GET, URL, status=429)
    responses.add(responses.GET, URL, status=429)
    responses.add(responses.GET, URL, status=200, json={"ok": True})
    session = RetryableSession(max_retries=_MAX_RETRIES, backoff_factor=0.0)
    result = session.get(URL)
    assert result.status_code == 200
    assert len(responses.calls) == 3
```

### E. Надуманные / нереалистичные сценарии
**Симптом.** Название/докстринг подразумевает риск («не зависает»,
«защищает от дедлока»), но не объяснено, откуда риск и в каком реальном
сценарии он проявился бы.

**Как чинить.**
- Добавь в докстринг причину: что именно в реализации могло бы привести
  к этому поведению без теста (конкретный механизм, а не общие слова).
- Если обоснования не находится — вынеси в отчёт вопрос, стоит ли тест
  оставлять, вместо тихого удаления/сохранения.
- Замени искусственные фикстуры на реалистичные (реальные форматы
  логов/задач и т.п.), а не абстрактные заглушки под конкретную проверку.

---

### F. Мёртвый код и бесполезные обёртки
**Симптом.** Неиспользуемые хелперы; константы-алиасы без причины
(`_PARSER_CONFIG_FILENAME = _PARSER_CONFIG_JSON`); константы/методы/классы
(включая фейки-заглушки), оставшиеся после переписывания или удаления теста.

**Как чинить.**
- Удали неиспользуемое полностью — grep по файлу/модулю на отсутствие
  использований.
- Алиасы constant → замени все использования старого имени на каноническое,
  само старое имя удали. Одно имя на одно значение.
- Для общих фейков/фикстур проверяй grep’ом весь пакет `tests/`, не только
  текущий файл — они нередко живут в `conftest.py` и используются соседними
  модулями.

---

### G. Неоправданное использование тестовых классов
**Симптом.** `class Test...` без общего состояния между тестами (нет
`self`, `setup_method`, фикстур уровня класса) — класс как визуальный
разделитель.

**Как чинить.** Класс оправдан только при реальном общем
состоянии/подготовке — иначе разворачивай в плоские функции. Группа
параметризованных тестов с общим `setup_method` (после слияния по
категории C) — законный повод для класса.

---

### H. Непонятные докстринги и артефакты генерации
**Симптомы:**
1. Расплывчатая формулировка правила («YAML приоритетен» — при каком
   именно условии?) вместо точного проверяемого утверждения.
2. Испорченный текст — разорванное переносом строки слово
   (`"""C\noreconfigManager...`) — артефакт LLM-генерации/копипаста.
3. Докстринг пересказывает реализацию (приватные методы, внутренние
   `if/else`) вместо краткого описания наблюдаемого поведения и критических
   оговорок сценария (что замокано, что реально).
4. «Защитная» лексика («защищает от того, что...») вместо прямого
   утверждения о поведении: не «защищает от X», а «поднимает ConfigError,
   если Y».
5. Докстринг/описание/комментарий не на русском (или смесь языков) —
   кодовая база `autodoc` ведётся на русском, расхождение недопустимо.

**Как чинить.** Переформулируй в одно точное утверждение; почини
разорванные слова; убери пересказ реализации, оставь поведение + критичные
оговорки сценария; замени «защитную» лексику на прямое утверждение;
переведи на русский все докстринги/описания/комментарии в затронутом
файле — переводом и уточнением формулировки занимайся одним заходом.

---

### I. Слабый ассерт вместо содержательного
**Симптом.** `assert result is not None` там, где рядом уже есть/можно
сделать строгую проверку типа/значения/структуры (обычно то же дублирование,
что в категории C).

**Как чинить.** Если строгая проверка есть отдельно — слить с этим тестом
(категория C). Если нигде нет — усилить сам ассерт: `isinstance(...)` и/или
конкретные значения релевантных полей вместо `is not None`.

---

### J. Неканонический порядок импортов
**Симптом.** Импорты не сгруппированы блоками: стандартная библиотека →
сторонние пакеты (`pytest`, `yaml`, `pydantic`...) → локальные модули
проекта (`autodoc.*`, `tests.*`), с пустой строкой между блоками и
алфавитным порядком внутри блока.

**Как чинить.** Перегруппировать в три блока в указанном порядке.

```python
# Было
import pytest
from pathlib import Path
import yaml
from autodoc.config.manager import ConfigManager
from typing import Any

# Стало
from pathlib import Path
from typing import Any

import pytest
import yaml

from autodoc.config.manager import ConfigManager
```

---

### K. Неиспользуемые переменные без `_`
**Симптом.** Переменной (в т.ч. при распаковке кортежа/`for`) присвоено
значение, которое дальше нигде не читается, но имя не `_`.

**Как чинить.** Неиспользуемые переменные и позиции распаковки → `_`.

```python
# Было
result, status_code = call_something()
# Стало
result, _ = call_something()
```

---

### L. Маркер теста не соответствует заявленной категории
**Симптом.** Маркер (`business_logic`/`contract`/`infrastructure`/
`integration`) выбран «на глаз» или скопирован с соседнего теста, а не по
факту сетапа/ассертов. Определения (из `pytest.ini`):
- `business_logic` — бизнес-правило предметной области.
- `contract` — совместимость протокола/интерфейса (например, тип
  возвращаемого значения — схема, а не «сырой» dict).
- `infrastructure` — механика фреймворка, subprocess, детали HTTP.
- `integration` — два и более настоящих коллаборатора работают вместе.

**Как чинить.** Для КАЖДОГО теста в файле (не только при слиянии) —
сверь маркер с тем, что тест реально проверяет по сетапу и ассертам, а не
с докстрингом или соседним тестом-донором. Маркер должен ДЕЙСТВИТЕЛЬНО
отражать заявленную категорию: если декларирует одно, а по факту
(HTTP/файловая система/только проверка типа/несколько реальных
коллабораторов) — другое, замени на подходящий, а не оставляй как есть.
На грани двух категорий — выбирай ту, что описывает главную проверяемую
вещь, а не побочный эффект сетапа.

---

### M. Входные данные теста не используют существующие ресурсные файлы
**Симптом.** Тест вручную собирает входные данные в теле (словарь-константа,
`json.dumps`/`yaml.dump`, запись через `tmp_path`) там, где в проекте уже
есть подходящий committed-ресурс (`tests/unit/<пакет>/resources/...`) или
фикстура-обёртка над ним (`resources_dir`, `valid_parser_config` и т.п. из
`conftest.py`). Дублирование одного набора полей вручную в нескольких
модулях вместо переиспользования ресурса — тот же симптом (см. также F).

**Как отличить.** Не любой inline-словарь — проблема: точечная
мутация/граничный случай конкретного поля («не-dict на верхнем уровне»,
«битый YAML», «explicit vs автозаполнение») законно остаётся inline —
ресурс под это заводить не нужно. Категория M — только про случаи, когда
тест просто гоняет «валидный конфиг/набор опций» без специфичной мутации.

**Как чинить.**
- Сначала проверь `resources/` рядом с тестируемым модулем и `conftest.py`
  на этом уровне и выше — подходящий ресурс и фикстура могут уже быть.
- Ресурс есть, но не используется → замени inline-данные на существующую
  фикстуру или прямое чтение из `resources_dir`.
- Ресурса нет, а сценарий — просто «валидный базовый случай» → заведи файл
  в `resources/` по аналогии с существующими + фикстуру в `conftest.py`,
  вместо хардкода в теле теста.
- Не переводи в ресурсы кейсы, которые по смыслу требуют испорченного/
  сгенерированного на лету содержимого — они законно остаются inline.

```python
# Было — вручную собирает конфиг, который уже есть как ресурс
# (tests/unit/config/resources/valid_parser_config.json)
def test_config_manager_load_parser_config_returns_correct_type(tmp_path: Path) -> None:
    data = {"platform_version": "2.0", "ci_prefix": "/ci-2.0/", ...}
    config_file = tmp_path / "parser_config.json"
    config_file.write_text(json.dumps(data), encoding="utf-8")
    manager = ConfigManager(configs_dir=tmp_path)
    assert isinstance(manager.load_parser_config("parser_config.json"), ParserConfigSchema)

# Стало — переиспользуем существующий ресурс через фикстуру
def test_config_manager_load_parser_config_returns_correct_type(
    tmp_path: Path, valid_parser_config: dict,
) -> None:
    """load_parser_config() возвращает экземпляр ParserConfigSchema для валидного конфига."""
    config_file = tmp_path / "parser_config.json"
    config_file.write_text(json.dumps(valid_parser_config), encoding="utf-8")
    manager = ConfigManager(configs_dir=tmp_path)
    assert isinstance(manager.load_parser_config("parser_config.json"), ParserConfigSchema)
```

## 3. Общие принципы

- Параметризация — дефолт для однотипных кейсов (различаются только
  входом/ожидаемым результатом при идентичной структуре).
- Комментарии-намерения при параметризации переезжают вместе с кейсом
  (над `pytest.param` или через `id=`).
- Классы — только под общее состояние, не как тематическая полка (G).
- HTTP/сетевые тесты — через `responses`, не ручной patch внутренностей (D).
- Маркеры должны соответствовать сути теста — для каждого теста в файле,
  не только при слиянии (L).
- Импорты — каноническими блоками: stdlib → сторонние → локальные (J).
- Докстринги — краткое описание поведения + критическая информация,
  без пересказа реализации и без «защитной» лексики (H).
- Докстринги/описания/комментарии — на русском, консистентно с кодовой
  базой (H).
- Неиспользуемые переменные и позиции распаковки — через `_` (K).
- Входные данные теста — по возможности через существующие ресурсные
  файлы/фикстуры, а не хардкод в теле теста (M).
- Sanity-check: тест должен краснеть при поломке кода проекта и не
  краснеть при поломке только сторонней библиотеки/математики.

---

## 4. Что НЕ делать

- Не переписывать тесты вне чек-листа из стилистических предпочтений.
- Не удалять тестовые кейсы молча при слиянии — перенести или обосновать.
- Не менять `autodoc/*` «заодно» — баги отдельным пунктом в отчёте.
- Не выдумывать фикстуры/ресурсы, которых нет — сначала проверить
  `conftest.py` и `resources/` рядом с файлом (M).

## 5. Формат отчёта

```
tests/unit/common/test_retryable_session.py
- [A] Удалён тест на арифметику backoff (test_backoff_grows) — не относится к RetryableSession.
- [D] test_retryable_session_retries_on_429 переписан на responses: проверяет
      фактическое поведение при 429, а не содержимое retry.status_forcelist.
```

Файлы без правок в отчёт не включать.
